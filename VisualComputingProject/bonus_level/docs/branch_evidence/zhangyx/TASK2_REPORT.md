# Bonus Task 2 - Just Dance Pose-Matching Application

## Goal and implementation

The application displays an annotated reference dancer and a live webcam dancer side by side. It detects the player with YOLOv8n Pose, compares the two poses, and displays immediate feedback (`PERFECT`, `GREAT`, `GOOD`, or `MISS`), total points, average similarity, and combo count.

No model training is required or performed. The supplied pretrained `yolov8n-pose.pt` model supplies 17 COCO keypoints.

## Runtime architecture

Task 1 preprocesses the reference video once and saves `pose_cache.npz`. Consequently, Task 2 performs only one pose inference stream at runtime: the webcam. This is important on the tested CPU-only environment.

The GUI and inference run independently:

1. Tkinter advances the reference video using a monotonic clock at the cached playback rate.
2. A worker thread reads mirrored webcam frames and runs YOLO pose inference.
3. The GUI consumes only the newest completed webcam result, so inference never blocks reference playback or the interface.
4. Tkinter widgets are updated only on the main thread.

## Pose normalization

Absolute image coordinates are unsuitable because the reference and player can appear at different positions and scales. Each pose is therefore translated around the hip center (falling back to the shoulder center or body-joint centroid) and divided by a robust body scale derived from shoulder width, hip width, torso length, and visible-body extent.

Scoring uses the 12 body joints from shoulders to ankles. Face keypoints are intentionally excluded because facial detections add little dance information and are sensitive to image resolution.

## Similarity score

Two complementary measurements are combined:

- **Angle similarity (65%)**: Gaussian similarity of eight elbow, shoulder, hip, and knee angles, using a 32-degree tolerance.
- **Normalized joint-position similarity (35%)**: Gaussian similarity of corresponding normalized joints, with extra weight on wrists and ankles.

The result is reduced when too few corresponding body joints are visible. Final similarity is clipped to 0–100. When mirror acceptance is enabled, the scorer checks both the direct pose and an anatomically left/right-swapped horizontal mirror and uses the better result.

## Temporal alignment

People naturally react after the reference dancer moves. At every new webcam result, the system compares the player against all cached reference poses from the current time back through the previous 0.8 seconds. The highest-scoring pose is used and the detected lag is displayed. This improves fairness without allowing a player to match future movements.

## Game feedback

| Similarity | Feedback | Points | Combo |
|---:|---|---:|---|
| 85–100 | PERFECT | 1000 | increases |
| 70–84.99 | GREAT | 700 | increases |
| 55–69.99 | GOOD | 400 | increases |
| below 55 | MISS | 0 | resets |

One score event is generated for each newly completed webcam inference, rather than for every GUI refresh.

## Verification results

The included reference output contains 300 annotated frames and 300 cached pose records at 10 FPS, giving a 30-second round. All 300 processed frames contained a primary dancer. `just_dance_app.py --check` confirmed an exact video/cache length match and a self-match score of 100.00.

Five deterministic scoring tests pass:

1. Identical poses score approximately 100.
2. Translation and uniform scaling do not reduce the score.
3. An incorrectly positioned arm is penalized.
4. A mirrored pose is recognized when mirror acceptance is enabled.
5. Temporal search locates the correct pose two frames behind the current reference.

## Limitations

- The tested PyTorch build is CPU-only. Webcam inference is therefore slower than reference playback, although the GUI remains responsive and scores every available result.
- Single-frame pose comparison cannot judge movement speed or rhythm as directly as a learned temporal model.
- Heavy occlusion, leaving the frame, or low light can reduce visible-joint coverage and score reliability.
- The included demonstration round is 30 seconds long. A longer game can be generated by increasing `--max-frames`; preprocessing time and cache/video size increase accordingly.
